# ↩ CRLF の誤検出をどこで止めるか（Issue #169）

## 🎯 要約

`bin/lint-md.sh` が CRLF の作業ツリーで CI と違う件数を返す問題を直した記録
である（`v2.19.3`）．対象ファイルを LF 正規化した複製の側で lint する形へ
変えた．作業した中で得たものは 5 つある．Issue の前提が実測と食い違った．
正規化の粒度を誤ると別の指摘が壊れる．突合の失敗は止める側へ倒した．
変異そのものが適用されない事故もあった．レビュー返信の投稿も静かに壊れた．

## 🗺 目次

- 🔍 Issue の前提は半分だけ正しかった
- ✂ 正規化の粒度を誤ると別の指摘が壊れる
- 🛑 突合できないときは止める
- 💥 変異が適用されないまま「落ちない」と読んだ
- 📮 レビュー返信の投稿が exit 0 のまま壊れた

## 🔍 Issue の前提は半分だけ正しかった

Issue #169 と #187 はいずれも「80 字ちょうどの文が 81 字と誤検出される」と
書いていた．再現を試みたところ，最初の 2 回は再現しなかった．

再現したのは 3 回目である．条件は **文が行をまたぐとき** であった．
`ja-technical-writing/sentence-length` は文の字数を数える．
文が段落内で折り返されていると，行末の `\r` がその文の内側へ入る．
一方，行末が `．` で終わる文では，`\r` は文の切れ目のあとに来る．
次の文の先頭の空白として捨てられるため，字数へ影響しない．

<!-- textlint-disable ja-technical-writing/ja-no-mixed-period -->

表 1. プローブの形と再現の有無

<!-- textlint-enable ja-technical-writing/ja-no-mixed-period -->

| プローブ | 再現 |
|---|---|
| 80 字の文を 1 行で置く（前後は空行） | しない |
| 80 字の文を段落の途中の行に置く | しない |
| 内容 79 字 + 改行 1 字を 2 行へ分けた 1 文 | する |

`settings` 側で観測された 6 件が「長い段落の途中で折り返した文」に偏って
いたのは，この条件による．前提を鵜呑みにしたまま「直った」と判断していれば，
効いていない修正を入れていた可能性がある．

再現しない段階で「Issue が間違っている」と結論づけなかったのは，
プローブの作り方を疑う余地が残っていたためである．
**再現しないことは，現象が無いことの証明にならない．**

## ✂ 正規化の粒度を誤ると別の指摘が壊れる

最初の実装は `tr -d '\r'` であった．Codex の指摘で 2 つの穴が分かった．

単独の `\r` も消える．`\r` は改行ではないため，消すと行が連結される．
CI の checkout には残っている内容なので，複製だけが別物になる．
指摘の消失と誤検出の両方が起こりうる．

代案の `sed 's/\r$//'` も採らなかった．末尾改行の無いファイルへ改行を足す
実装があり，`MD047`（末尾改行の有無）の判定を変えてしまう．

採ったのはバイト列の置換である．`data.replace(b"\r\n", b"\n")` なら，
どちらの副作用も原理的に起きない．
`scripts/normalize-lint-targets.py` へ切り出し，pytest で 3 点を固定した．
単独 CR が残ること，末尾改行を足さないこと，CRLF が LF へ寄ること．

**「行末の CR を消す」と「CRLF を LF にする」は別の操作である．**
前者の言い方で実装すると，改行でない CR まで巻き込む．

## 🛑 突合できないときは止める

textlint は checkstyle 出力へ絶対パスを書く．集計は複製のルートを prefix と
して剥がし，リポジトリルート相対へ戻してから対象一覧と突き合わせる．

剥がせなかったパスは対象一覧と一致しない．その指摘は捨てられる．
lint 自体は成功しているため，利用者には「指摘なし」の 0 終了として見える．
Windows では大小文字・8.3 名・ジャンクションの解決有無で表記が割れうる．

選択肢は 2 つあった．表記を正規化して通すか，剥がせないことを検出して
止めるかである．**止める側を採った．**
どの表記を同値とみなすかはボリュームの設定に依存し，中央側で決め切れない．
判定を緩めると「検査したつもり」の状態が増えるだけである．

`scripts/check-report-paths.py` を集計の前へ置いた．
判定規則は `count-lint-findings.py` の `_strip_workspace_prefix` と同一とした．
**片方だけ緩いと，通した先で黙って捨てられる．**

これは既存の規律「絞り込む設計は失敗が沈黙する」の追加事例である．
今回の学びは，沈黙を止める場所として **絞り込みの直前** を選んだ点である．
絞り込んだ後では，何が消えたかを知る手がかりが残らない．

## 💥 変異が適用されないまま「落ちない」と読んだ

修正の効きを確かめるため，正規化を外す変異を掛けた．
1 度目は `sed` の置換パターンが実際の行と一致せず，変異が適用されなかった．
にもかかわらず lint は走り，出力も返った．

このとき出力は「誤検出なし」であった．変異が効いていれば誤検出が出るはず
である．つまり **「変異しても落ちない」と読める出力が返っていた．**
置換の確認に入れておいた `grep` が無出力だったことで気づいた．

規律は 2 つある．

- 変異は適用されたことを確かめてから測る．
  置換後に該当行を表示し，目当ての形になっていることを見る．
- 使い捨ての変異でも `sed` の引用に頼らない．
  Python スクリプトへ書き，一致しなければ `assert` で止める．

既存の規律「対処を消してテストが落ちるか確かめる」には，
**変異が本当に入ったかを確かめる段** が抜けていた．
入っていない変異は，何も証明しない．

## 📮 レビュー返信の投稿が exit 0 のまま壊れた

Codex の inline comment へ返信するとき，
`gh api ... -f "body=@path"` と書いた．
`gh api` の `-f`（`--raw-field`）は値を literal として送る．
`@file` を読むのは `-F`（`--field`）だけである．

結果として，返信本文がローカルの絶対パス文字列のまま投稿された．
コマンドは成功し，`html_url` も正常に返る．
ユーザーの指摘まで気づけなかった．

`gh pr comment --body-file` の癖で「`@file` は展開される」と思い込んだ．
2026-07-09 に `gh pr create --body @'...'@` で本文へ `@` が混入した件と
同じ型である．**長い本文を外部から渡す工程は，exit 0 のまま壊れる．**

投稿系コマンドの直後は本文を読み返す．
壊れた投稿は消さずに直せる．review comment なら次のとおりである．

```bash
gh api --method PATCH repos/O/R/pulls/comments/<id> -F body=@file
```

規律の反映先は `tomio2480/settings` Issue #380 とした．
本リポジトリ固有の話ではないためである．

併せて，調べ方の罠も 1 つ記録する．
`gh issue list -R O/R --search "..."` が，そのリポジトリに存在しない Issue を
返した．番号を引用する前に `gh issue view <n> -R O/R` で実在を確かめる．

## 📌 残った判断

- 複製へ入れるのは対象ファイルだけとした．
  報告は対象ファイルへ絞られるため，対象外の指摘は元から捨てられている．
  ただし `markdownlint-cli2` のディレクトリ別設定は複製に無い．
  サブディレクトリで設定を分ける caller が現れたら再検討する．
- 明示引数が非 Markdown だけのとき，複製に glob 一致が 0 件になりうる．
  変更前は 0 終了で，変更後の振る舞いは未実測である．
- 変更は `bin/lint-md.sh` に閉じる．
  composite action と reusable workflow の契約は変わらないため，
  caller 側の対応は不要である．
