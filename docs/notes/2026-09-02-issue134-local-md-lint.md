# push 前ローカル lint の実装で得た知見

## 要約

Issue #134（PR #162，v2.15.0）で `bin/lint-md.sh` を実装した過程の記録である．
Codex のレビューを 5 巡受けて 13 件を修正し，そのうち 8 件が同じ失敗形だった．
「lint の結果を対象ファイルへ絞り込む」設計は，絞り込みの入力が壊れると
**指摘が黙って消えて 0 終了する** ．本稿はその構造と，設計上の対処を残す．
あわせて Windows 固有の落とし穴と，レビューの使い分けを記録する．

## 目次

- 🕳 沈黙する失敗という構造
- 🧭 押し出し方向へ倒す

## 🕳 沈黙する失敗という構造

本ツールは lint を glob 全体へ掛け，報告だけを変更ファイルへ絞り込む．
CI の summary と同じ `count-lint-findings.py --diff-files-from` を使うためである．

この形には固有の弱点がある．**絞り込みの入力（対象一覧）が壊れると，
lint は正常に走っているのに報告が 0 件になる** ．
lint の失敗と違い，出力は「指摘なし」で，終了コードは 0 である．
push 前ゲートとしては最悪の壊れ方で，利用者は検査されたと信じてしまう．

実際に見つかった経路を挙げる．いずれも独立した原因から同じ結末に至る．

表 1. 対象一覧が壊れて報告が消えた経路．

| 壊れ方 | 原因 |
|---|---|
| 名前がエスケープされる | `core.quotePath` の既定で git が 8 進表記を出す |
| 名前が別物になる | 読み手が `strip()` して先頭の空白を落とす |
| 相対の基準が違う | 呼び出し時のカレント基準のまま集計へ渡す |
| 一覧が空になる | `mapfile` が process substitution の状態を継がない |
| 一覧が空になる | 実在しないパスを検査せず受け取る |
| 一覧が空になる | glob の解釈を誤り対象を選び損ねる |
| 一覧が空になる | 基点が `HEAD` へ落ちコミット済み変更を含まない |

7 通りの原因があって，症状は 1 つである．
症状から原因を辿れないため，1 件ずつ潰すしかなかった．

## 🧭 押し出し方向へ倒す

対処は個別の修正だけでは足りない．非対称性を設計へ入れる．

**選定は多めに選ぶ側へ倒す．** 対象一覧は「報告を絞り込む集合」であって
指摘の発生源ではない．多く選んでも後段の集計が落とすだけだが，
少なく選ぶと指摘が消える．害が釣り合わない．

この原則を適用した結果，`--glob` の解釈をやめた．
当初は拡張子を取り出し，`{md,markdown}` を展開し，解釈できない記法を
判定する 35 行を持っていた．そこから 2 度取りこぼしを出した．
選定側で glob を再実装する限り，取りこぼす方向の穴は開き続ける．
`--glob` が渡されたら絞り込まない，と決めて機構ごと削った．

**沈黙させない．** 基点の解決順を直すだけでなく，選ばれた基点を毎回表示する．
`HEAD` へ落ちたことが見えれば，対象 0 件を「変更なし」と読み違えない．
機械的な正しさより，人の気づける形のほうが効く場面もある．

## 🪟 Windows 固有の落とし穴

3 件を踏んだ．いずれもテストで検出でき，実機確認で気づいたものもある．

- **Python の標準出力がロケール依存になる．**
  リダイレクト先へ書くとき既定が cp932 になり，日本語の指摘が化ける．
  `PYTHONUTF8=1` と `PYTHONIOENCODING=utf-8` を明示して固定した．
- **パス形式が 2 種類ある．**
  Git Bash の `pwd` は `/c/...` を，`git rev-parse --show-toplevel` は
  `C:/...` を返す．素朴な文字列比較は成立しない．
  相対化は `git rev-parse --show-prefix` に委ね，集計へ渡す workspace は
  `pwd -W` を優先する．
- **`.sh` に CRLF が混入する．**
  Python の `write_text` は既定で改行を変換する．`.gitattributes` の
  LF 指定に反し，ShellCheck が全行へ `SC1017` を出して gate が落ちる．
  シェル資産の編集に汎用スクリプトを使わない．

## 🔍 レビューの使い分け

Codex と Fable で見つかるものが違った．

- **Codex** は差分を行単位で厳密に読む．`mv` の宛先が既存ディレクトリの
  ときの意味論，`mapfile` の bash 4 依存など，仕様書に当たらないと
  分からない点を確実に拾う．一方，巡回を重ねると病的な入力へ向かい，
  4 巡目以降は「symlink が通常ファイルへ置き換わった `.md`」のような
  現実に起きない条件が増えた．
- **Fable** には差分全体と Issue の意図を渡して通し読みさせた．
  Codex が 5 巡で見つけられなかった「既定ブランチが `main` でない
  リポジトリで基点が `HEAD` へ落ちる」を 1 回で拾った．
  加えて「この機構は利益に見合わない」という削る方向の指摘を出した．
  これは行単位のレビューからは出てこない．

**使い分けの目安**．行単位の厳密さは Codex，設計意図との突き合わせと
機構の削減は Fable とする．後者はレビューの終盤に 1 回置くと効く．

## 🧱 継ぎ足しが生む退行

5 巡の対応で，直近 4 件のうち 2 件は自分の前の修正が作った不具合だった．
`mv` の意味論の誤りと，拡張子なし `--glob` の取りこぼしである．
後者は「解釈できない記法では絞り込まない」と決めた同じ回に，
拡張子なしのケースだけ既定へ落とす分岐を残したものだった．

指摘が新規欠陥を減らす速度と，修正が新規欠陥を生む速度が近づいたら，
追加のレビュー巡回ではなく通し読みへ切り替える合図とする．

## 📌 残した判断

- **`bin/lint-md.ps1` は作らない．** PowerShell での再実装は PR を肥大化させる．
  Windows は Git Bash 経由とし，docs へ明記した．
- **依存キャッシュで待たない．** 競合に負けた時点で自分の `npm ci` は
  完了している．待って得られるのは staging 1 つ分のディスクだけである．
- **`-z` による NUL 区切りは採らない．** 下流の `--diff-files-from` が
  改行区切りの契約で，CI の summary と共有している．
  報告された失敗自体は `core.quotePath=false` で解消する．
