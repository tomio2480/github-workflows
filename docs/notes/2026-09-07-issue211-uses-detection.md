# 🔍 検査の道具を，問いの難しさに合わせる（Issue #211）

## 要約

`uses:` が引用符付きだと pin 検査を素通りする穴（Issue #211）を塞ぐ作業で，
穴を 3 巡にわたって作り直した．原因は「その `uses` は mapping の鍵か，
文字列の中身か」という問いへ，行単位の正規表現で答えようとしたことである．
判定を PyYAML の解釈へ移して解消した．
本ノートは，見逃しと誤検出が交互に出る状況をどう読むかを残す．

## 📉 何が起きたか

Issue #211 の内容は「引用符付きの `uses:` を pin と違反のどちらへも収集できない」である．
正規表現へ引用符の許容を足せば済む，という見立てで着手した．

レビューを 3 巡かけた結果，同じ検出器から次が出た．

<!-- textlint-disable ja-technical-writing/ja-no-mixed-period -->

表 1. 巡ごとに見つかった欠陥の件数

<!-- textlint-enable ja-technical-writing/ja-no-mixed-period -->

| 巡 | 見逃し | 誤検出 |
|---|---:|---:|
| 1 巡目（Claude） | 3 | 0 |
| 2 巡目（Claude） | 0 | 2 |
| 3 巡目（Codex） | 3 | 2 |

見逃しは「YAML としては成立するのに，どの区分にも入らない書き方」である．
値を次行へ置く形，flow mapping，コロン前の空白，引用符付きの鍵，
compact sequence の中の兄弟の鍵が該当した．

誤検出は「`uses` の鍵ではないのに違反として報告する」である．
コメント中の記述，半角コンマを挟んだ地の文，block scalar の中身，
flow mapping の中の引用符付きの値が該当した．

いずれも実測で再現してから対応した．レビューの主張を鵜呑みにせず，
正規表現へ直接当て，`yaml.safe_load` で YAML としての成立も確かめた．

## 🔁 なぜ 3 巡かかったか

**指摘を個別の欠陥として読み，個別に塞いだためである．**

1 巡目の指摘は 3 つの書き方だった．書き方を 3 つ足せば済むと読んだ．
2 巡目の指摘は誤検出だった．範囲を絞れば済むと読んだ．
3 巡目で見逃しと誤検出が同時に出て，はじめて共通の原因を見た．

共通していたのは，どの欠陥も **同じ 1 つの問いへ帰着する** ことである．

> その `uses` は mapping の鍵か，文字列の中身か．

この問いに答えるには，鍵の引用と値の引用を解く必要がある．
block scalar の指示子，compact sequence の字下げ，flow mapping の構造も要る．
これは YAML の parser がしていることそのものである．
行単位の正規表現でこれを再実装しようとしていた．

**見逃しと誤検出が交互に出るのは，道具が問いに足りていない徴候である．**
片方を直すともう片方が出るのは，判定の境界を手で引き直しているためである．
1 種類だけが続くうちは個別に塞いでよい．交互に出たら，道具を疑う．

## 🧭 判断の分かれ目

parser を使う案は当初から挙がっていた．採らなかった理由は依存である．
`scripts/check-action-pins.py` は `workflow-lint` composite action から呼ばれる．
caller の runner でも走るため，依存を足すと実行環境に条件が増える．

この判断が誤りだった．**依存を避けた結果，正しさを失った．**

決め直す際に測ったのは次の 2 点である．

- `ubuntu-latest` に PyYAML が導入済みか．**導入済みだった（実測 6.0.1）．**
  取得の経路は通らない．避けようとしていた条件は，実際にはほぼ生じない．
- 導入できない場合にどうするか．検査を省くと素通りと区別が付かないため，
  明示的に落とす．`MissingYamlSupport` を投げ，CLI が原因を名指しして終わる．

行単位の収集は残した．pin の報告には行番号が要り，版コメントは parser が捨てる．
**parser は「どこに鍵があるか」を決め，行は「そこに何が書いてあるか」を読む．**
役割を分けたことで，どちらも無理をしなくなった．

## 🧪 テストの形

書き方の一覧そのものをテストへ固定した．

- `_USES_FORMS`: `uses` の鍵が現れる 19 通りを，`pin`・`unpinned`・
  `unrecognized`・`none` のどの区分へ入るかと組で並べる．
  **区分が 1 つに定まらないこと自体を失敗とする．** 0 なら素通り，
  2 以上なら二重計上である．
- `_VALID_DOCUMENTS`: 正しく書かれた 7 通りを並べ，1 件も報告しないことを見る．

誤検出の表を持つ意味は大きい．**落ちる gate は外される．**
誤検出は見逃しと同じだけ検査を損なう．片方だけを守る表では足りない．

新しい書き方を許すときは，表へ 1 行足してから実装を触ることになる．

## ⚠️ 副次的に踏んだ罠

**push 前の gate をパイプへ入れた．**

```sh
bash bin/lint-md.sh 2>&1 | tail -4 && git push
```

パイプラインの終了コードは最後のコマンドのものになる．
`lint-md.sh` が指摘ありで非 0 を返しても `tail` の 0 が `&&` へ渡り，
textlint の指摘 2 件を残したまま push した．
出力は目の前に出ていたが，`&&` が止めると思い込んでいた．

出力を絞りたい動機と，失敗で止めたい動機が同じ 1 行の中で衝突する．
絞る側が黙って勝つ．gate は単独で実行し，終了コードを見てから次へ進む．
