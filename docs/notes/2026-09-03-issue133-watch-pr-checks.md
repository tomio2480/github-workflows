# Issue #133（`watch-pr-checks`）の実装で得た知見

## 要約

PR #166（v2.16.0）で `bin/watch-pr-checks.{sh,ps1}` を追加した．
その過程で得た知見を残す．中心は 2 つの失敗である．
1 つは自作の監視ツールが自ら false green を出したこと．
もう 1 つは，その対処を守るテストが仕様を守れていなかったことである．
どちらも「pass した」という報告だけでは気づけない種類の失敗であった．
あわせて `--watch` を捨てた設計判断と，PowerShell 版のテスト方法も記す．

## 目次

- 知見 1: 監視ツールが自ら false green を出した
- 知見 2: テストが仕様を守れていなかった
- 知見 3: ブロックする外部コマンドには締切を掛けられない
- 知見 4: PowerShell 版は関数で外部コマンドを覆ってテストする

- 参照

## 知見 1: 監視ツールが自ら false green を出した

開発の途中，このスクリプト自身で PR #166 の CI を監視したところ，
次を報告した．

```text
watch-pr-checks: all 1 checks passed on 48292b2...
```

裏を取ると CI は 1 つも起動していなかった．
`gh run list --commit 48292b2` は空を返した．
実際に見ていたのは，push 直後に付く CodeRabbit の status 1 件だけである．
workflow の登録は約 1 分後であった．

原因は完了条件の弱さである．
当時の条件は「1 件以上あり，pending が無く，件数が前回の照会から
増えていない」であった．据え置きが 1 間隔（既定 10 秒）しかない．
登録の遅れがそれを超えると，先に見えた check だけで完了と読む．

対処は据え置きを秒数にすることである．
`--settle` 秒のあいだ件数が動かないことを要求する形へ変えた．
既定は観測した遅延の 2 倍である 120 秒とした．
等倍にしなかったのは，手前の待機が短い日ほど余裕が消えるためである．

**教訓は「静かであること」と「出そろったこと」は別だという点にある．**
観測の間隔が短いと，前者を後者と読み違える．
同じ筋で `skipping` の扱いも決めた．
path filter で飛ばした check を通過件数へ数えず，`(N skipped)` として別に示す．
「検査した」と「検査を飛ばした」を報告で同じにしない．

当初の実装は総数へ skip を含めたまま括弧書きだけを足していた．
`pass` 1 件と `skipping` 1 件で「all 2 checks passed」と出る形である．
記録が実装より先に「混ぜない」と書いており，Codex のレビューが食い違いを突いた．
指摘を受けて実装側を記録へ寄せた．あわせて，すべて skip の場合は
「all 0 checks passed」ではなく `no checks ran` と出す．
通過 0 件を全 pass と読ませると，path filter の設定ミスが green として沈黙する．

なお残余は消えていない．`--settle` より後に現れる check は追えない．
本来これは GitHub 側の required checks で担保する筋である．
本リポジトリの `main` に required checks は設定していない．

## 知見 2: テストが仕様を守れていなかった

知見 1 の対処を入れた時点で，bats 20 件が pass していた．
そのうち 2 件は，守るべき仕様を守れていなかった．

1 つは据え置きのテストである．
スタブは 2 回目の照会で 2 件目を出していた．
件数の据え置き 1 回で完了するため，秒数の判定を丸ごと消しても通る．
つまり知見 1 の対処そのものを検出できない．

もう 1 つは「件数が増え続ける」経路のテストである．
`--timeout 0` で書いていたため，初回照会の直後に必ず締切へ達していた．
増え続ける挙動を 1 度も観測しておらず，スタブを差し替えても通る．

対処として，前者は 3 回目の照会で現れるスタブを足し，
`--interval 1 --settle 2` の組で検証する形へ変えた．
**秒数の条件を実際に外して落ちることを確認してから直した．**
後者は締切を 2 秒とし，照会が 3 回以上起きたことも併せて検証する．

**教訓は，テストの pass も「検査した」を意味しないという点にある．**
知見 1 と同じ形の誤読である．
対処を入れたときは，その対処を消すと落ちるかを 1 度確かめる価値がある．

## 知見 3: ブロックする外部コマンドには締切を掛けられない

当初は `gh pr checks --watch` を使っていた．
レビューで「`--timeout` が効かない」と指摘され，設計を変えた．

`--watch` は checks が完了するまでブロックし，中断の手立てを持たない．
pending の check が居座ると，締切の判定へ到達しないまま待ち続ける．
締切を被せるには background 実行と `kill` の管理が要り，
bash と PowerShell で挙動をそろえにくい．

そこで `--watch` を捨て，状態を自前で polling する形へ変えた．
待つ側が制御を握れば，締切の判定は while の中へ自然に収まる．
副産物として，終了コードの解釈も不要になった．
`fail`・`cancel` の件数がそのまま判定の材料になるためである．

**継ぎ足しで守れない性質は，機構ごと差し替えたほうが簡単になる場合がある．**

判定の材料を出力だけにした点も重要である．
`gh pr checks` は pending で exit 8，failure でも非 0 を返しつつ結果を出す．
終了コードで判定すると，検査中の PR を照会失敗と誤読する．
実際 PowerShell 版だけがこの誤読を抱えており，レビューで見つかった．

## 知見 4: PowerShell 版は関数で外部コマンドを覆ってテストする

`bin/*.ps1` には振る舞いのテストが無く，静的解析しか掛かっていなかった．
実際 1 巡目のレビューで見つかった不具合は PowerShell 版だけにあった．

`shell-quality.yml` は Pester 6.1.0 を導入済みであった．
`docs/shell-quality.md` にも「対象が無いため実行しない」と書いてある．
受け皿は用意されていた．
そこで `tests/powershell/` を作り，`bin/verify-shell.py` から
`bin/run-pester.ps1` 経由で実行する形にした．

スタブの置き方には工夫が要る．
PATH へ実行ファイルを置く方法は，拡張子と実行権限の扱いが
Windows と Linux で違うため避けた．
代わりに同一セッションで `gh`・`git` の関数を定義して覆う．
関数の探索は呼び出し元のスコープまで遡るため，
対象スクリプトからは外部コマンドに見える．
対象が `exit` を呼ぶので，`stub-runner.ps1` を子プロセスとして起動し，
`$LASTEXITCODE` から終了コードを取り出す．

この方式の落とし穴も 1 つ記す．
`param` ブロックを持つスクリプトへ `-Pr` のような引数を渡すと，
共通パラメーター `-ProgressAction` の前方一致で吸われる．
`$args` で素通しすれば避けられる．

スタブは実物から離れうる．
`--json` のフィールド列を引用符なしで書き，PowerShell がカンマで
配列へ分割した不具合は，スタブが素通ししていたため実 PR で初めて出た．
以後はスタブ側でも `--json` の値が 1 語であることを検査している．

**スタブが緩いと，テストは「通ってしまう」．**

## 知見 5: レビューのティアと，判断が割れたときの残し方

Codex を 3 巡（7 件）と Fable の通し読み（10 件）を受けた．
役割は明確に分かれた．

Codex は行単位で仕様と実装のずれを挙げる．
`--timeout` が効かない，終了コードの解釈が違う，fork の head を
解決していない，といった指摘である．いずれも実在した．

Fable は設計意図との突き合わせと，機構の削減を見る．
テストが仕様を守れていない（知見 2），据え置きの既定に余裕が無い，
`skipping` を pass に混ぜている，といった指摘である．
これらは行を追うだけでは出てこない．

**巡を重ねるたびに実在の欠陥が出る間は，もう 1 巡の価値がある．**
今回は 3 巡目でも 2 件出た．

2 者の判断が割れた箇所もある．fork からの PR への対応である．
Codex は追加を求め，Fable は削除を求めた．
残す判断を採った．理由は失敗の出方である．
削除した場合の失敗は「静かに待ち続ける」であり，
本スクリプトが防ごうとしている誤認そのものになる．
両論と採った理由は `docs/development-notes.md` に残した．
