## 🧩 prh を検出専用に転用する設計

prh は expected への置換を前提とする辞書だが，定型句の指摘には
機械的な置換先が存在しない場合がある．本対応では次の整理で成立させた．

- 機械置換できる語（`不可欠` → `必要`，`に他ならない` → `である`）は
  通常どおり expected に置換先を書く．
- 置換先がない語は expected を（）付きのガイダンス文字列とする．
- この転用が成立する前提は，中央 action の CI 経路が
  checkstyle → reviewdog であり，fix 情報を使わない点にある．
  caller が独自に `--fix` を有効化するとガイダンス文字列が本文へ
  混入するため，注意書きを [docs/rule-rationale.md](../rule-rationale.md) に残した．

`必要不可欠` の扱いでは，長一致を先に置く alternation と
否定戻り読み `(?<!必要)` を併用し，二重置換と重複検出を防いだ．
`ユーザー` ルール等の否定先読み設計と同系の考え方である．

## 🧪 収録判断の実測手順

出典 Gist の候補は 20 語超あるが，v1 は 7 語に絞った．判断手順は次のとおり．

1. 候補語句をリポジトリ内 Markdown へ grep し，出現頻度を実測する
   （textlint のローカル導入はせず，使い捨て診断にとどめる）．
2. 全候補 0 件だったため，grep 自体の動作を既知語（`リポジトリ`: 113 件）で裏取りした．
3. 本リポジトリで実害ゼロでも caller 側の過剰マッチは測れないため，
   正当用法の多い語（`言及する`・`〜において` 等）を除外し，
   `.textlint-allowlist.yml` を逃げ道として明記した．

除外理由を採否と同じ場所（`docs/rule-rationale.md`）へ記録したことで，
再提案時に同じ検討を繰り返さずに済む．

## 🔍 レビュー対応の判断記録

`gemini-code-assist` の 7 指摘のうち採用は 1 件（ひらがな表記
`にほかならない` の追加）で，6 件は根拠を添えて却下した．

- 「`正面から回収する` は誤字では」という指摘（2 件）は，
  出典 Gist に当該表現が明示されていることを確認して却下した．
  レビュー指摘の出典突合を実践した事例である．
- 活用語尾までマッチ範囲を広げる提案（4 件）は，語幹一致が
  全活用形を 1 パターンで覆う意図的設計である点を示して却下した．
  optional 接尾辞は検出範囲を広げず，差はハイライトの見た目のみである．

Bot 指摘は「もっともらしいが出典と食い違う」場合がある．
機械的に採用せず，一次情報（出典・実測）と突き合わせてから採否を決める．

## 🏷 タグ運用の遅延に関する気づき

マージ後の patch タグ運用（`vX.Y.Z` ＋ `v2` 追従）が
`v2.5.10` 以降の 6 マージ分で未発行だった．
「PR マージごとにタグを切る」規律はセッションをまたぐと漏れやすい．
セッション末尾フローの点検項目としてタグ位置の確認を加えると再発を防げる．
