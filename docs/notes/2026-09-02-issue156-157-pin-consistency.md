# 📓 Issue #156・#157・#160: pin 整合の機械化で得た知見

## 要約

`templates/` の `actions/checkout` が 3 メジャー遅れていた問題（#156）と，版コメントの書き方が 2 種類混在していた問題（#157）を片付けた．いずれも Dependabot の走査が届かない領域で起きている．規律ではなく検査で守る形へ移し，`tests/python/test_action_pins.py` を置いた．本ノートは，このとき得た 4 つの知見を残す．検査は「検出できない形」を先に潰すこと，積み重ね PR の base を消すと依存 PR が閉じること，`gh` の応答は push 直後に古びること，SHA は推測で書かないことである．

## 📌 背景

Issue #153（v2.14.2）で Dependabot の走査範囲を `directories` へ移し，ネストした composite action を対象へ入れた．その直後にリポジトリ内の全 pin を点検して 2 件が見つかった．

1 件目は `templates/.github/workflows/md-lint.yml` の `actions/checkout` である．v4.3.1（2025-11-13）で止まり，中央側の v7.0.1 から 3 メジャー遅れていた．`templates/` は caller 用の雛形であって本リポジトリの workflow として実行されない．そのため走査対象へ入れても Dependabot は扱わない．構造的に取り残される領域である．

2 件目は版コメントの書き方である．行末（`@<SHA> # v7.0.1`）が 5 箇所，直上行（`# actions/checkout v7.0.1` を置いて次行に `uses:`）が 8 箇所あった．Dependabot が書き換えるのは行末だけである．直上行は残置され，レビューのたびに手で補正する工程を生む．#153 で composite action が走査対象へ入ったぶん，補正が要る箇所は 6 から 8 へ増えていた．

## 🔍 知見 1: 検査は「検出できない形」を先に潰す

#157 で追加した検査は，最初の実装で目的を果たしていなかった．版コメントを `\S+` で拾い，直後に行末アンカーを置いていたためである．

```python
r"(?:\s*#\s*(?P<version>\S+))?\s*$"
```

この形だと `# actions/checkout v7.0.1` の行は行全体がマッチしない．マッチしない行は収集処理が黙って捨てる．結果として **本 PR が排除しようとしている書き方そのものが，どの検査にも掛からない** 状態だった．Codex のレビューが指摘した．

検査を書くときは，正常な入力を通すことより，異常な入力が収集の網から落ちないことを先に確かめる．落ちた入力は「指摘ゼロ」として現れる．偽 green は，検査が無い状態より悪い．無ければ人が見るが，あれば人は見なくなる．

同じ理由で，収集が空振りする場合も fail させている．pin を 1 件も拾えないとき，`templates/` と `.github/` のどちらか片方しか読めていないときの 2 つである．

修正の効きは実ファイルで確かめた．`md-lint.yml` の行末コメントを一時的に `# actions/checkout v7.0.1` へ書き換えると，修正前は 0 件だった指摘が 2 件として現れる．**検査を直したら，直った検査が実際に発火することまで見る．**

## ⚠️ 知見 2: 積み重ね PR の base ブランチを消すと依存 PR が閉じる

PR #159 は PR #158 の上に積み，base を `chore/issue156-templates-checkout-pin` に置いていた．#158 を `gh pr merge --delete-branch` でマージしたところ，base を失った #159 が GitHub に自動クローズされた．

閉じた PR は base を変更できない（`Cannot change the base branch of a closed pull request`）．復旧は次の順で行う．

1. 消した base ブランチを同じ commit へ復元する．
2. 依存していた PR を `gh pr reopen` する．
3. `gh pr edit --base main` で付け替える．
4. 復元したブランチを削除する．

この手順ならレビューコメントと返信は保持される．新しい PR を作り直すと履歴を失う．

**積み重ね先がある間は `--delete-branch` を使わない．** 依存 PR の base を先に main へ付け替えてから消す．GitHub は base ブランチ削除時に自動リターゲットすることがあるが，マージと同時の削除では間に合わなかった．

## 🕐 知見 3: `gh` の応答は push 直後に古びる

新しいコミットを push した直後，`gh pr view --json headRefOid` は 1 つ前の commit を返し続けた．`gh run list` にも新しい run が現れない．「CI が起動していない」と読み，空コミットでの再トリガーを考えかけた．

実際にはリモートも CI も正常だった．`git ls-remote origin <branch>` はその時点で新しい commit を指しており，しばらく後に `gh` の側が追いついた．

**リモートの実体は `git ls-remote` で見る．** `gh` の応答だけで「反映されていない」と判断しない．CI の起動有無を疑うのは，実体の確認が済んでからでよい．

## 🔢 知見 4: SHA は推測で書かない

知見 2 の復旧で base ブランチを復元する際，フル SHA を短縮形から推測して書き，push に失敗した．`git rev-parse` で解決すれば 1 手で済む．

同種の失敗は `gh release create --target` でも過去に起きている（短縮 SHA を 422 で拒否される）．**40 桁が要る場面では必ず `git rev-parse` を通す．**

## 🧭 設計判断の記録

### 規律ではなく検査で守る

`templates/` の pin ずれは，リリース前チェックの手順書へ 1 行足す対応でも塞げる．採らなかった．Issue #142 で学んだとおり，構造的に生じるずれは規律の徹底では消えない．版コメントのドリフトは 4 回再発している．

`templates/` を Dependabot の走査対象へ入れられない以上，ずれは今後も生じ続ける．検出は機械へ任せ，人は判断だけを担う形にした．検査は既存の `unit-python` job がそのまま拾うため，workflow 側の変更は要らなかった．

### 検査の対象範囲から `docs/` を外す

Issue #160 として起票し，同じ PR で片付けた．結論は「範囲を広げない」である．

起票時に `docs/` を走査したところ，実 SHA は `docs/development-notes.md` の 2 箇所のみだった．いずれも PR #143 の差分引用である．Dependabot が行末コメントを自動更新する証拠として置いており，**古い側の SHA と版が残ることに意味がある**．検査へ入れると直しようのない指摘になる．

オンボーディング手順も SHA を `git/refs/tags` から変数へ解決する形で，固定 SHA を書き下していない．守るべき対象が 1 つも無いため，理由の明文化にとどめた．

**起票の前に対象を数える．** 「検査していない領域がある」は，それ自体では問題ではない．

### SHA と版の対応は CI で検査しない

追加した検査はリポジトリ内部の一貫性だけを見る．同じ SHA へ 2 通りの版が書かれていないことは確かめるが，その SHA が本当に v7.0.1 かは確かめない．上流への問い合わせが要り，CI をネットワークへ依存させるためである．

手で pin を写す場面では，`gh api repos/<owner>/<repo>/git/ref/tags/<tag>` で突合する．#157 では版コメントを移す前に 14 箇所すべてを突合し，annotated tag は object を 1 段辿って比較した．全件一致したため版表記はそのまま写している．
