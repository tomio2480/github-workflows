# タグ運用ドリフトと版コメント齟齬から得た知見

## 背景

対象は次の 2 件である．
Issue #75 は md-lint caller テンプレへの `timeout-minutes` と `concurrency` の追加である．
Issue #76 は claude-review 実行時の cache 書き込み拒否警告である．
この対応セッションで，タグ運用と版コメントに関する 3 件の見落としが連鎖して発生した．
いずれも訂正済みだが，再発防止のため判断パターンとして記録する．

- PR #77（Issue #75 対応）：`v2.6.2` 発行．問題なし
- PR #78（Issue #76 対応，ドキュメントのみ）：タグ発行を誤って省略 → `v2.6.3` で訂正
- PR #79（版コメント齟齬修正，`# v2.6.3` と記載）：`v2.6.4` 発行．
  記載時点で最新タグを確認せず「次は v2.6.3 だろう」と推測した．
  そのため実際のタグ番号（`v2.6.4`）とコメント内容が 1 つずれた
- PR #81（版コメントを `# v2.6.5` へ確定）：最新タグを
  `git tag --sort=-v:refname` で確認し，次番号を確定した．
  `v2.6.5` を発行して収束

## 判断 1：ドキュメントのみの変更でも patch タグは省略しない

PR #78 は README・`docs/security.md` への注記のみで，動作コードの変更はなかった．
この際「動作コード変更なしだからタグ不要」と自己判断し，タグ発行を省略した．

直後に `git log` と `git tag` の対応関係を確認した．
過去の PR #74（同じくドキュメントのみ）には `v2.6.1` のタグ発行実績が見つかった．
誤りに気づき，`v2.6.3` を追加発行した．

判断軸は次のとおり．

- CLAUDE.md の「PR マージごとに `vX.Y.Z` patch タグを切る」に変更種別（コード／
  ドキュメント）による例外規定はない．
- 「今回は不要だろう」と判断しかけたら，まず過去の同種 PR にタグが付いているかを
  `git log --oneline` と `git tag` の対応で確認してから判断する．独断で規律の
  適用範囲を狭めない．

## 判断 2：`v2` タグはオンボーディング手順の実データ取得元である

PR #79（版コメント齟齬修正）のタグ発行要否をユーザーに問われた際，
「機能や説明の実質的な変更がない限りタグ不要では」という論点が出た．

確認の結果，`v2` タグは単なる目印ではなく，README のオンボーディング手順が
実際に参照するデータソースだと判明した．

```bash
SHA=$(gh api "repos/${OWNER}/github-workflows/git/refs/tags/v2" --jq '.object.sha')
curl -fsSL ".../${SHA}/templates/.github/workflows/md-lint.yml" ...
```

`v2` を動かさない限り，新規オンボーディングするユーザーは修正前の
テンプレート（古い版コメントを含む）を取得し続ける．
「ドキュメントを直した」だけでなく「`main` には反映されているが `v2` 経由の
配布物には未反映」という実害のある状態になる．

汎用化すると次のヒューリスティックになる．

> **タグ・ブランチの参照先が「単なる目印」か「実際のデータ取得元」かを区別する**
> 後者に該当する場合，「見た目の変更が軽微だから」という理由でタグ追従を
> 省略すると，参照経路を通じて配布される成果物が古いまま固定される．

## 判断 3：template バージョンコメントは release ごとに更新する規律の再確認

対象は `templates/` 配下の `md-lint.yml` と `claude-review.yml` の版コメントである．
`# vX.Y.Z` 併記コメントが，それぞれ `v2.5.0`／`v2.6.0` のまま
3 リリース分（`v2.6.1`〜`v2.6.3`）更新漏れしていた．

この規律自体は `docs/development-notes.md` に明文化済みである．
該当節は「template バージョンコメント bump をチェックリスト化する」である．
過去にも PR #28（v2.3.0）・PR #30（v2.4.0）で同種の漏れが指摘されていた．今回の漏れは新しい発見ではなく，
**既知の規律をリリース作業の都度チェックできていなかった** ことが原因である．

対応として，リリース（タグ発行）作業のたびに以下を確認する運用を徹底する．

1. `templates/.github/workflows/*.yml` 内の `# vX.Y.Z` 併記コメントを
   grep する．発行する patch タグと一致しているか確認する．
2. 一致しない場合は同一 PR かリリース直前の追加コミットで補正する．

## 判断 4：版コメントの番号は「書く前」に確定する．「書いた後」に合わせない

PR #79 で `# v2.6.3` と記載したが，マージ時点で実際に付与されたタグは
`v2.6.4` だった．原因は構造的な限界ではなく，**手順の順序ミス** である．

版コメントは「このコミット自身が属するリリースのバージョン」を書く自己参照的な
値であり，タグ発行という別ステップで初めて番号が確定する．
このとき「次はおそらく vX.Y.Z だろう」と推測で書くと，並行する別修正
（今回は PR #78 の訂正タグ）が先に番号を消費していた場合にずれる．

正しい手順は次のとおり．

1. 版コメントを書く **前** に `git tag --sort=-v:refname | head -1` で
   現在の最新タグを確認する．
2. その次の patch 番号を確定し，コメントへ記載する．
3. コミット・マージ後，**間を置かず** 同じ番号でタグを打つ．
   他の作業を挟んで後回しにしない．

汎用化すると次のヒューリスティックになる．

> **将来決まる値を先取りして書く場合は，書く前に「今何が最新か」を確認する．**
> 「後で答え合わせをする」のではなく「先に答えを確定してから書く」順序を守る．

## まとめ

4 件はいずれも「規律は文書化済みだが，実行時に確認せず自己判断・推測した」ことが
根本原因である．次回以降は以下を徹底する．

- タグ要否を迷ったら，まず過去の同種 PR の扱いを確認する．
- タグ・ブランチが「単なる目印」か「実データの参照先」かを確認してから
  省略可否を判断する．
- リリース作業時は `templates/` 配下の版コメントの grep 確認を
  チェックリストに含める．
- 将来のタグ番号をコメントへ書く際は，書く前に最新タグを確認して確定し，
  マージ直後に間を置かず同じ番号でタグを打つ．
