# タグ運用ドリフトと版コメント齟齬から得た知見

## 背景

Issue #75（md-lint caller テンプレへ `timeout-minutes` と `concurrency` を追加）と
Issue #76（claude-review 実行時の cache 書き込み拒否警告）への対応セッションで，
タグ運用と版コメントに関する 2 件の見落としが発生した．
いずれも訂正済みだが，再発防止のため判断パターンとして記録する．

- PR #77（Issue #75 対応）：`v2.6.2` 発行．問題なし
- PR #78（Issue #76 対応，ドキュメントのみ）：タグ発行を誤って省略 → `v2.6.3` で訂正
- PR #79（版コメント齟齬修正）：`v2.6.4` 発行

## 判断 1：ドキュメントのみの変更でも patch タグは省略しない

PR #78 は README・`docs/security.md` への注記のみで，動作コードの変更はなかった．
この際「動作コード変更なしだからタグ不要」と自己判断し，タグ発行を省略した．

直後に `git log` と `git tag` の対応関係を確認したところ，過去の PR #74
（同じくドキュメントのみ）が `v2.6.1` として既にタグ発行されていた実績が見つかり，
誤りに気づいて `v2.6.3` を追加発行した．

判断軸は次のとおり．

- CLAUDE.md の「PR マージごとに `vX.Y.Z` patch タグを切る」に変更種別（コード／
  ドキュメント）による例外規定はない．
- 「今回は不要では」と判断しかけたら，まず過去の同種 PR にタグが付いているかを
  `git log --oneline` と `git tag` の対応で確認してから判断する．独断で規律の
  適用範囲を狭めない．

## 判断 2：`v2` タグはオンボーディング手順の実データ取得元である

PR #79（版コメント齟齬修正）のタグ発行要否をユーザーに問われた際，
「機能や説明の実質的な変更がない限りタグ不要では」という論点が出た．

確認の結果，`v2` タグは単なる目印ではなく，README のオンボーディング手順が
実際に参照するデータソースだと判明した．

```bash
SHA=$(gh api "repos/${OWNER}/github-workflows/git/refs/tags/v2" --jq '.object.sha')
curl -fsSL ".../${SHA}/templates/.github/workflows/md-lint.yml" ...
```

`v2` を動かさない限り，新規オンボーディングするユーザーは修正前の
テンプレート（古い版コメントを含む）を取得し続ける．
「ドキュメントを直した」だけでなく「`main` には反映されているが `v2` 経由の
配布物には未反映」という実害のある状態になる．

汎用化すると次のヒューリスティックになる．

> **タグ・ブランチの参照先が「単なる目印」か「実際のデータ取得元」かを区別する**
> 後者に該当する場合，「見た目の変更が軽微だから」という理由でタグ追従を
> 省略すると，参照経路を通じて配布される成果物が古いまま固定される．

## 判断 3：template バージョンコメントは release ごとに更新する規律の再確認

`templates/.github/workflows/md-lint.yml` と `claude-review.yml` の
`# vX.Y.Z` 併記コメントが，それぞれ `v2.5.0`／`v2.6.0` のまま
3 リリース分（`v2.6.1`〜`v2.6.3`）更新漏れしていた．

この規律自体は `docs/development-notes.md`「template バージョンコメント
bump をチェックリスト化する」に既に明文化されており，過去にも PR #28（v2.3.0）・
PR #30（v2.4.0）で同種の漏れが指摘されていた．今回の漏れは新しい発見ではなく，
**既知の規律をリリース作業の都度チェックできていなかった** ことが原因である．

対応として，リリース（タグ発行）作業のたびに以下を確認する運用を徹底する．

1. `templates/.github/workflows/*.yml` 内の `# vX.Y.Z` 併記コメントを
   grep し，発行する patch タグと一致しているか確認する．
2. 一致しない場合は同一 PR かリリース直前の追加コミットで補正する．

## まとめ

3 件はいずれも「規律は文書化済みだが，実行時に確認せず自己判断した」ことが
根本原因である．次回以降は以下を徹底する．

- タグ要否を迷ったら，まず過去の同種 PR の扱いを確認する．
- タグ・ブランチが「単なる目印」か「実データの参照先」かを確認してから
  省略可否を判断する．
- リリース作業時は `templates/` 配下の版コメントの grep 確認を
  チェックリストに含める．
