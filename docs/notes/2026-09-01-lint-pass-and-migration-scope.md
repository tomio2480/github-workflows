# 緑の CI と，移行の洗い出し範囲についての知見

## 背景

2026-09-01 のセッションで Issue #142 と PR #143 を処理した．
前者は版コメントの major 限定化，後者は Dependabot の受領である．
それぞれ v2.13.4 と v2.13.5 として発行した．

本ノートは変更内容そのものではなく，作業中に露見した 2 つの誤りを残す．
いずれも「確認したつもりで確認できていなかった」型である．
版コメント変更の判断そのものは
[2026-09-01-issue142-version-comment-major-only.md](2026-09-01-issue142-version-comment-major-only.md)
にある．

## 判断

### CI の pass は「指摘ゼロ」を意味しない

PR #144 の初回 push で，CI チェック 6 件はすべて pass した．
しかし lint summary には textlint の error が 3 件出ていた．

本リポジトリの composite action は `fail_on_error: false` で reviewdog を動かす．
lint 指摘では job を落とさない設計である．
設定・setup の実行エラーだけが job を失敗させる．
したがってチェックの緑は「実行が成功した」までしか保証しない．

確認すべきは summary コメントの件数表である．
差分側とリポジトリ全体の両方が 0 であることを見る．
併せて `検査対象:` 行が最新コミットを指すことも確かめる．
古い run の summary を読んでいる事故を防ぐためである．

これは既存の知見「チェック名の pass を検査範囲の証拠にしない」と対になる．
あちらは **何を** 検査したかの話であり，こちらは **合否が何を意味するか** の話である．

### 移行では「実ファイル」と「説明文中の例」を分けて洗い出す

版コメントを `# v2` へ移行する作業で，初回の洗い出しに漏れが出た．
Codex レビューで 3 箇所を指摘され，追加調査でもう 1 箇所を見つけた．

原因は検索語の選び方である．
`# v2.13.3` という実値で grep したため，実ファイル 3 件は拾えた．
一方，説明文が既定として示していた `# v2.2.0` は架空のバージョンであり，
実値の検索には掛からなかった．

実ファイルだけを直すと，説明は旧形式を既定として示し続ける．
読み手には移行が中途半端に見え，patch 形式へ戻す動機が残る．
今回はまさに，同じファイルの中で 10 行目と 189 行目が矛盾する状態になっていた．

表記の移行では次の順で洗う．

1. 実値（`# v2.13.3` など）で grep し，実ファイルを特定する．
2. 形式（`# v[0-9]+\.[0-9]+\.[0-9]+`）で grep し，説明文中の例を特定する．
3. 拾った箇所ごとに「既定を主張しているか」「代替として明示しているか」を分ける．

3 の区別は要る．今回は「代替 2（完全固定）」の説明として
`# v2.0.0` を意図的に残した．すべてを機械的に置換すると，
選択肢の説明まで消えてしまう．

### ローカルの簡易検査は，本物の判定条件を写せていないと役に立たない

push 前に文長と漢字連続を自作スクリプトで検査したが，違反を検出できなかった．
リンクを含む行を丸ごと除外していたためである．

textlint の `sentence-length` は，リンクのテキストが URL やパス形式のときだけ
長さの計算から外す．行ごと無視するわけではない．
除外条件が本物より広く，見るべき行を落としていた．

さらに，強調記法の内側にある句点は文の境界として扱われない．
`**……した．**` と書くと次の文と結合し，2 文ぶんの長さで判定される．
自作の正規表現分割ではこの挙動を再現できなかった．

教訓は，簡易検査を作るなら「見落とし」ではなく「過検出」側へ倒すことである．
リンクを含む行も検査対象に残し，誤検出は目視で捨てるほうが安全である．
Issue #134（中央設定を直接実行する push 前 lint）が解こうとしているのは，
まさにこの「本物の判定条件を写す」問題である．
